## Context

I built a Simon-says style memory game on a Raspberry Pi expecting the challenge to be game logic. Instead, the project became an exercise in coordinating independent systems: hardware, a Python controller, a web interface, and a shared database.

For my Internet of Things course, each assignment has us add our own creative component, involving the hardware, software, or both. The idea for this project had been in my head since the class started, so actually getting to implement it was very exciting.

## System Overview

The game was split into four cooperating parts:

- Raspberry Pi Python program - drives LEDs and reacts to shared state
- Firestore - acts as the synchronization layer between hardware and UI
- Web interface - captures player input and displays progress
- Physical wiring - constrains what the software can observe and control

Each component was simple individually, but the complexity came from keeping them synchronized.

The LED bar consumed 10 GPIO pins, leaving limited choices for the RGB LED. The tutorial diagrams only showed components individually, so combining them required carefully planning the hardware layout before writing code. The wiring effectively determined what the program could represent.

## State Flow

A round follows this sequence:

1. Python generates a random color to add to the sequence
2. The RGB LED flashes the sequence and adds the random color to the end
3. The player repeats the sequence on the red/green/blue buttons provided by the web interface
4. Firestore updates accordingly to check the player's inputs
5. If all the player's inputs are correct, the led bar lights the next led to indicate the round's completion

The difficulty was ensuring each step completed properly before the next began.

The program was less about game logic and more about synchronizing events across systems. Any step happening early or late caused visible inconsistencies between the UI and hardware, which broke the illusion of a consistent sequence.

## What I Expected

I expected the difficulty to come from generating and checking sequences: the actual game logic.
Instead, the majority of effort went into coordinating events between the hardware, Python runtime, and web interface.

## Takeaways

I had a lot of fun bringing this idea to life. Nearly all of the coding in my coursework thus far has been purely software, so actually learning some electronics hands-on has been a blast.

The logic itself was trivial once the systems agreed, but the challenge was ensuring they agreed at the same time. Building hardware-integrated software felt less like writing an algorithm and more like orchestrating events.
